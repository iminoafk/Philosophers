01

A dinner party where you can starve to death

Before any code: what this program simulates, why it's famous, and what it prints when you run it.

The setupThe rules of the table

Philosophers sit around a round table. Between each pair of neighbours lies one fork. A philosopher needs two forks — the one on their left and the one on their right — to eat.

Each one loops forever: eat, sleep, think, repeat. If a philosopher goes too long without eating, they die and the whole dinner stops.

🍝

Eat

Requires holding both neighbouring forks at once. Takes time_to_eat milliseconds.

😴

Sleep

Forks are put back on the table. Nobody is blocked. Takes time_to_sleep ms.

💭

Think

Waiting for a turn. This is where hunger quietly builds — and where deaths happen.

💀

Die

If time_to_die ms pass since their last meal started, they're gone and the program ends.

🎓
This is a famous problem, not a made-up exercise

Edsger Dijkstra invented "the Dining Philosophers" in 1965 to demonstrate concurrency bugs that are otherwise almost impossible to explain. The forks are a stand-in for any limited resource that many parts of a program fight over: a database connection, a file, a slot in memory.

Watch it runReal output, replayed at the real speed

Below is the actual output of ./philo 4 410 200 200 3 — 4 philosophers, dead after 410ms without food, 200ms to eat, 200ms to sleep, stop once everyone has eaten 3 times. Press play and watch the table and the log together.

👀
Notice the pattern: 1 and 3 eat, then 2 and 4 eat

Nobody coordinated that. There is no scheduler, no turn-taking list, no central manager. Four independent workers, each following simple local rules, produced a perfectly alternating pattern. That emergent order is the achievement of this program — and modules 4 and 6 show the two tricks that cause it.

The entry pointWhere the program starts

Every C program starts at a function called main. Here it is — the whole thing is five checks in a row.

philo.c — main()
code 
int	main(int ac, char **av)
{
	t_data	*data;

	if (ac < 5 || ac > 6)
		return (ft_putstr_fd("Error ! Wrong Arguments... [4 - 5]\n", 2), 1);
	if (!parse_value(ac, av))
		return (ft_putstr_fd("Error ! Wrong Values...\n", 2), 1);
	data = fill_data_struct(ac, av);
	if (!data)
		return (ft_putstr_fd("Error ! Initialization failed.\n", 2), 1);
	if (!start_simulation(data))
		return (destroy_data(data),
			ft_putstr_fd("Error ! Simulation failed.\n", 2), 1);
	destroy_data(data);
	return (0);
}
plain english

The program begins here. ac is how many words the user typed; av is the list of those words.

Reserve a slot for data — the box that will hold the whole simulation's state.

Check 1: did they give us 4 or 5 numbers? (ac counts the program's own name too, hence 5 and 6.) If not, complain and quit.

Check 2: are all those numbers positive whole numbers? "Zero philosophers" or "banana milliseconds" gets rejected here.

Build the world: allocate memory, create the locks, create the philosophers. If it handed back NULL — C's way of saying it did not work — say so and quit.

Run the dinner. This one line takes seconds or minutes — everything in this course happens inside it.

Clean up and exit. Return 0, which by universal convention means "finished successfully."

🧭
Read this shape everywhere

Validate input → build state → run → clean up. That four-beat structure is the skeleton of almost every program ever written, from this 40-line file to a web server. When you ask an AI to write a CLI tool, this is the shape you should expect back.

The five numbersEverything the user controls

number_of_philosophersHow many diners — and therefore how many forks, and how many threads.
time_to_dieMilliseconds a philosopher can survive since their last meal began. The deadline everything else is measured against.
time_to_eatHow long a meal takes. During this time both forks are unavailable to the neighbours.
time_to_sleepHow long a nap takes after eating. Forks are already back on the table.
[must_eat_count]Optional. If given, the program stops cleanly once everyone has eaten this many times. If omitted, it runs until someone dies.

Square brackets are the universal convention for "optional argument" in command-line documentation. In the code that optionality shows up as must_eat = -1, a sentinel value meaning "no limit."

Meet the cast

Seven files, two data structures, and three kinds of characters. Learn who is who and the rest of the course reads itself.

The metaphorA stage play with three roles

Think of the program as a theatre production. There are actors who perform, a stage manager watching from the wings ready to drop the curtain, and the set — the props everyone shares.

🧑‍🍳
The philosophers — the actors

One thread each, all running the identical script (routine()). They never talk to each other directly. They only compete for props.

👁️
The monitor — the stage manager

One extra thread that performs nothing. It walks the line every millisecond checking "is anyone starving? is everyone finished?" and ends the show.

🍴
The forks and the shared data — the set

Props on the stage. Anyone can reach for them, but only one actor can hold a given fork at a time. Enforcing that is the entire difficulty.

A struct is a labelled box holding related values. t_data is the one box every thread shares.

Define a box type called t_data holding everything about the dinner.

The five numbers the user typed, stored as whole numbers.

Three more locks guarding three different things: printing, the stop flag, and meal records. Module 5 explains why three and not one.

*philos: the list of philosophers themselves.

Data structure 2t_philo — one diner

philosophers.h
code 
typedef struct s_philo
{
	int					id;
	pthread_t			thread;
	int					left_fork;
	int					right_fork;
	long				last_meal_ms;
	int					meals_eaten;
	t_data				*data;
}						t_philo;
plain english

One philosopher's personal record.

id: their number, 1 through N. This is what gets printed in the log.

thread: the handle to their running thread — how the main program later says "wait for this one to finish."

left_fork / right_fork: not the forks themselves, just which index in the shared fork list. Philosopher 0 uses forks 0 and 1.

last_meal_ms: when their last meal started. The monitor compares this against the clock to detect starvation.

meals_eaten: their personal counter, used for the optional "everyone ate N times" finish.

*data: a pointer back to the shared table, so each philosopher can reach the forks and the rules.

🔗
The back-pointer trick

Each philosopher carries *data, a pointer back to the shared world. That's why a thread can be handed exactly one thing — itself — and still reach everything. You'll see this same pattern as context, ctx, or props in every language you meet.

03

Threads: many hands, one memory

How one program runs five philosophers at the same time — and why "at the same time" is where every hard bug comes from.

The metaphorMultiple cursors in one shared document

Picture a Google Doc open on six laptops. Six cursors, six people typing independently — but one document. Nobody has their own copy. If two people edit the same sentence at the same instant, you get garbage.

That is exactly a thread. Six independent lines of execution, one shared memory.

📄 One cursor (normal code)

Line 1 runs, then line 2, then line 3. Predictable, easy to reason about, and only one thing happens at a time. This is called sequential execution. A philosopher would have to finish their entire life before the next one starts.

📄📄📄 Six cursors (threads)

Six copies of the same script run simultaneously on the same data. You get real simultaneity — and you lose all guarantees about what order things happen in.

⚠️
The order is genuinely unpredictable

The operating system decides which thread runs when, and it changes its mind constantly. Run this program twice with identical arguments and you will get different output both times. Any bug that depends on ordering may appear once in a thousand runs — which is why concurrency bugs are the ones AI assistants get wrong most often.

Launching themFive lines that start the whole dinner

simulation.c — start_simulation()
code 
	data->start_ms = get_time_ms();
	i = -1;
	while (++i < data->n_philo)
		data->philos[i].last_meal_ms = data->start_ms;
	i = -1;
	while (++i < data->n_philo)
		if (pthread_create(&data->philos[i].thread, NULL,
				routine, &data->philos[i]) != 0)
			return (0);
	if (pthread_create(&monitor, NULL, monitor_routine, data) != 0)
		return (0);
	i = -1;
	while (++i < data->n_philo)
		pthread_join(data->philos[i].thread, NULL);
	pthread_join(monitor, NULL);
plain english

Start the stopwatch. Record the current time as "moment zero" for the whole dinner.

Give everyone a grace period. Tell every philosopher their last meal was right now — otherwise the monitor would see "last ate: never" and kill them all instantly.

Launch each philosopher. pthread_create says: start a new thread, have it run the routine function, and hand it this philosopher's record. Repeat N times.

If launching a thread fails, bail out immediately and report failure upward.

Launch the watchdog — one more thread, running different code, handed the whole shared table instead of a single philosopher.

Now wait. pthread_join means "pause here until that thread finishes." The main thread sits on this line for the entire dinner.

Finally wait for the monitor too. Only when all N+1 threads are done does this function return.

🔑
Create then join — always both

Starting a thread and never joining it is one of the most common concurrency mistakes. Without the join, main would race ahead, hit destroy_data(), and free the memory that all the philosophers are still standing in. "Are all threads joined before cleanup?" is a great question to ask an AI that just wrote you threading code.

The shape of a thread functionWhy it returns void *

simulation.c
code 
void	*routine(void *arg)
{
	t_philo	*philo;

	philo = (t_philo *)arg;
plain english

Every thread function must have this exact shape: takes one anonymous pointer, returns one anonymous pointer. That's the contract pthread_create demands.

void * means "a pointer to something, and I'm not saying what." It's the C version of "any type" — it lets one function signature serve every possible use.

Reserve a properly-typed variable for our philosopher.

The cast: "this anonymous pointer is actually a philosopher — treat it as one." From here on the code can say philo->id.

🧩
Every thread API in every language does this

The thread library was written before this program existed and knows nothing about philosophers. So it accepts a generic pointer and lets you cast it back. In JavaScript or Python the same idea appears as a callback with a payload argument. Recognising the pattern in one language means recognising it in all of them.

04

The fork problem

Mutexes, deadlock, and the single odd/even line that stops the whole table from freezing forever.

The metaphorThe petrol station bathroom key

There's one key, chained to a hubcap, behind the counter. Take it and the bathroom is yours. Anyone else who wants in stands at the counter and waits — not politely, literally cannot proceed — until you bring it back.

That is a mutex. Each fork in this program is one.

pthread_mutex_initHave the key made. Done once at startup, in init_forks_data().
pthread_mutex_lockTake the key. If someone else has it, this line does not return — your thread freezes here until it's free.
pthread_mutex_unlockHand the key back. Exactly one waiting thread is now unfrozen.
pthread_mutex_destroyMelt the key down at the end, in destroy_forks(). Skipping this leaks resources.
🔒
A mutex protects nothing by itself

Nothing physically stops a thread from touching shared data without locking first. The lock only works because every piece of code agrees to ask for it. One function that forgets, and the protection is gone everywhere. That's why "which mutex guards this variable?" is the sharpest question you can ask about threaded code.

The dangerDeadlock: the one-lane bridge

Two cars enter a one-lane bridge from opposite ends and meet in the middle. Each will reverse only after the other does. Neither ever does. The bridge is closed forever.

Now the same thing with forks: if all five philosophers pick up their left fork at the same instant, every fork on the table is held, every philosopher is waiting for a right fork that will never be released, and the program hangs — silent, using no CPU, doing nothing, forever.

Step 0

The fixSix lines that break the circle

The deadlock needs a perfect ring of waiting: 1 waits on 2, 2 waits on 3, … 5 waits on 1. Break the ring anywhere and it cannot form.

simulation.c — take_forks()
code 
	if (philo->id % 2 == 0)
	{
		first = philo->left_fork;
		second = philo->right_fork;
	}
	else
	{
		first = philo->right_fork;
		second = philo->left_fork;
	}
	pthread_mutex_lock(&philo->data->forks[first]);
	print_status(philo, "has taken a fork");
	pthread_mutex_lock(&philo->data->forks[second]);
	print_status(philo, "has taken a fork");
plain english

Is my id an even number? % is the remainder operator — id % 2 is 0 for even ids, 1 for odd ones.

Even philosophers reach left first, right second.

Odd philosophers reach right first, left second. The opposite order.

Take the first fork — freeze here if someone has it. Announce it.

Take the second fork — freeze again if needed. Announce it. Now we hold both and can eat.

✅
Why reversing just some of them is enough

Deadlock requires everyone to reach in the same rotational direction. Flip half of them and you always end up with at least one pair reaching for the same fork first — one of them wins, the other waits, and that pair breaks the ring. This is called lock ordering, and it is the standard cure for deadlock in every system on earth.

Name the partsDeadlock needs all four of these

A deadlock can only exist when four conditions hold at once. Remove any one and it becomes impossible — which gives you four different places to attack.

🔐

Mutual exclusion

Only one holder at a time. Unavoidable here — a fork can't be shared.

✊

Hold and wait

You keep fork one while queuing for fork two. Some designs fix deadlock by grabbing both or neither.

🚫

No preemption

Nobody can snatch a fork from a holder. Some systems add timeouts to break this.

🔄

Circular wait

This is the one this code attacks. The odd/even swap makes a perfect ring impossible.

🤖
Steering an AI with this vocabulary

"It freezes sometimes" gets you guesses. "This can deadlock via circular wait on the fork mutexes — impose a global lock ordering" gets you the correct fix on the first try. Naming the failure mode is most of the work.

05

The referee and the shared whiteboard

One thread that watches everyone, one flag that stops everyone, and the reason this project uses three separate locks instead of one.

The metaphorThe lifeguard at the pool

Swimmers swim. They don't check on each other — they're busy. One person sits above the water doing nothing but scanning, every few seconds, for anyone in trouble. The moment they spot one, they blow the whistle and everybody gets out.

The monitor thread is that lifeguard. It never takes a fork and never eats. It only looks.

monitor.c — monitor_routine()
code 
	data = (t_data *)arg;
	while (!check_stop(data))
	{
		i = 0;
		while (i < data->n_philo)
		{
			if (is_dead(&data->philos[i]))
				return (print_death(&data->philos[i]), NULL);
			i++;
		}
		if (data->must_eat >= 0 && all_ate_enough(data))
			return (set_stop(data), NULL);
		usleep(1000);
	}
	return (NULL);
plain english

Unwrap the shared table from the anonymous pointer we were handed.

Keep patrolling for as long as nobody has raised the stop flag.

Walk the whole line of philosophers, one by one, from the first to the last.

Is this one starving? If yes: print the death message and stop patrolling immediately — the show is over.

Second question: if the user asked for a meal target, has everyone reached it? If so, raise the stop flag and exit — a happy ending, no death printed.

Sleep 1 millisecond, then look again. Without this the monitor would burn an entire processor core spinning as fast as it can.

⏱️
Polling: the humble pattern that's everywhere

Checking repeatedly on a timer is called polling. That usleep(1000) is the tuning dial: check more often and you detect death more precisely but waste more processor; check less often and a philosopher could be dead for 50ms before you notice. 1ms is the sweet spot when deadlines are measured in hundreds of milliseconds.

The hazardTwo people writing on one whiteboard

A shared whiteboard shows a number. Alice reads it (7), Bob reads it (7), Alice writes 8, Bob writes 8. Two increments happened; the board says 8. One update vanished — and no error was reported anywhere.

That's a race condition. It's why stop — a single integer — is never touched directly.

utils.c
code 
int	check_stop(t_data *data)
{
	int	stop;

	pthread_mutex_lock(&data->stop_mtx);
	stop = data->stop;
	pthread_mutex_unlock(&data->stop_mtx);
	return (stop);
}

void	set_stop(t_data *data)
{
	pthread_mutex_lock(&data->stop_mtx);
	data->stop = 1;
	pthread_mutex_unlock(&data->stop_mtx);
}
plain english

To read the stop flag safely:

Make a private scratch variable to copy it into.

Take the lock that guards this flag — nobody else may touch it now.

Copy the value out, then immediately release the lock. Hold it for two instructions, not a moment longer. The locked region is called the critical section.

Return the private copy. The caller reads a stable snapshot instead of a value that might change mid-read.

To raise the flag: same dance — lock, write, unlock. Short, symmetric, and impossible to get halfway through.

💡
"Even one integer needs a lock"

It's tempting to think a single int is too small to break. It isn't — on real hardware, one thread's write may sit invisible in a processor cache while another thread reads a stale copy for milliseconds. Wrapping every access in a tiny function like check_stop() means the rule is enforced in exactly one place and can't be forgotten at the call sites.

#lock-design · 4 members
P1
philosopher 1

Genuine question: why do we have print_mtx, stop_mtx AND meal_mtx? Wouldn't one big lock be simpler?

👁
monitor

Simpler to write, much slower to run. With one lock, you updating your meal count would block me from printing, and block P4 from reading the stop flag. Everyone queues behind everyone.

philosopher 4

So each lock covers one kind of data. Printing has nothing to do with meal counts, so they never wait on each other.

👁
monitor

Exactly. Engineers call it fine-grained locking. One giant lock is a "coarse" lock — correct, but it serialises everything and throws away the whole point of threads.

P1
philosopher 1

Downside? Three locks feels like three chances to make a mistake.

🖨
print_status

It is. The moment one thread takes locks A-then-B while another takes B-then-A, you've built a deadlock. Look at me: I take print_mtx, then call check_stop() which takes stop_mtx. print_death uses that same order deliberately — print first, stop second. Never the reverse.

👁
monitor

And that's the rule: every thread must take locks in the same global order. Same fix as the forks in module 4, one level up.

The printerWhy nothing prints after a death

utils.c — print_status()
code 
void	print_status(t_philo *philo, char *msg)
{
	long	t;

	pthread_mutex_lock(&philo->data->print_mtx);
	if (!check_stop(philo->data))
	{
		t = get_time_ms() - philo->data->start_ms;
		printf("%ld %d %s\n", t, philo->id, msg);
	}
	pthread_mutex_unlock(&philo->data->print_mtx);
}
plain english

The only place in the program that prints anything. Takes a philosopher and a message.

Take the printing lock. Without it, two philosophers printing simultaneously could produce 12 1 is 12 3 has taken a fork — genuinely interleaved characters.

Re-check the stop flag while holding the lock. This is the subtle part: it guarantees no "is thinking" can slip out after "died" has been printed.

Work out how long since the dinner began, then print timestamp id message — the exact format the log uses.

Release. The next philosopher queued at this line now gets their turn.

🎯
A single funnel for output

Every message in the program goes through this one function. That's why the log is always clean, always ordered, and always stops the instant someone dies. Whenever you have many workers writing to one place — a file, a console, a log service — one guarded funnel is the answer.

06

Fairness: nobody gets left behind

Avoiding deadlock isn't enough. A philosopher can be perfectly free to eat and still starve, because the fast ones never stop.

The metaphorThe potluck seconds rule

There's one dish left. You're hungry and you're standing right next to it — but you already had a helping, and you notice the person beside you hasn't had any. So you wait.

That single act of checking your neighbours before serving yourself is the entire content of should_wait(), and it's the difference between a dinner that survives and one that doesn't.

💀 Deadlock

Nobody makes progress. Everyone is frozen holding one fork. The program hangs silently and uses no CPU. Fixed in module 4.

😵 Starvation

Most make progress; one never does. The program looks perfectly healthy, output keeps flowing — and philosopher 3 quietly dies at 410ms. Fixed here.

🕵️
Starvation is the harder bug by far

Deadlock announces itself — everything stops. Starvation hides: the program runs, the log scrolls, and one participant is silently never served. The same shape shows up as one API caller always losing to the others, or one queue job never picked up. If an AI tells you "the deadlock is fixed," the follow-up question is always "and is it fair?"

The ruleCheck both neighbours before reaching

utils.c — should_wait()
code 
	left = &data->philos[(philo->left_fork - 1 + data->n_philo)
		% data->n_philo];
	right = &data->philos[philo->right_fork];
	pthread_mutex_lock(&data->meal_mtx);
	wait = 0;
	if ((data->must_eat < 0 || left->meals_eaten < data->must_eat)
		&& philo->last_meal_ms > left->last_meal_ms)
		wait = 1;
	if ((data->must_eat < 0 || right->meals_eaten < data->must_eat)
		&& philo->last_meal_ms > right->last_meal_ms)
		wait = 1;
	pthread_mutex_unlock(&data->meal_mtx);
	return (wait);
plain english

Find the philosopher on my left. The + n_philo then % is the classic trick for wrapping around a circle — it turns "one before philosopher 0" into "the last philosopher" instead of a crash.

Find the philosopher on my right. Simpler: their index is already stored.

Lock the meal records before reading anyone's numbers — those are being updated by other threads constantly.

Assume I don't need to wait, then look for a reason to.

Left neighbour: if they still need meals, and my last meal was more recent than theirs (meaning they're hungrier), then I hold back.

Right neighbour: identical check on the other side.

Release the lock and report back: should I wait, yes or no?

⏳
"Later last meal" means "less hungry"

philo->last_meal_ms > left->last_meal_ms reads as "I ate more recently than they did." A bigger timestamp means a more recent meal, which means less hunger. Timestamps compared as plain numbers trip people up constantly — always translate to "more recent" out loud.

Where it's usedThe waiting room

simulation.c — top of take_forks()
code 
	while (!check_stop(philo->data) && should_wait(philo))
		usleep(300);
	if (check_stop(philo->data))
		return (0);
plain english

Loop while two things are both true: the dinner hasn't been called off, and a neighbour is hungrier than me.

Pause 300 microseconds, then re-check. Not a fixed delay — a re-evaluation. The instant my neighbour eats, their timestamp updates and I'm free to go.

Escape hatch: if we left the loop because the program is stopping (not because it's my turn), return 0 — which tells routine() to break out and finish, without taking any forks.

🧠
Two exits, two meanings

This little loop can end for a good reason (my turn) or a bad one (shutdown), so the code checks which immediately after. Any wait-loop in any program needs this — a loop that can only end one way will hang forever the day something unexpected happens.

07

When it breaks

Concurrency bugs don't crash — they lie. Here's how to catch them, including one that's actually in this code right now.

The metaphorThe symptom that stops when the doctor walks in

The most frustrating patient complaint is the intermittent one: the noise your car makes right up until the mechanic listens. Threading bugs behave exactly like this — and worse, the act of observing changes them.

Add a print statement to find a race condition and the print's timing can hide the very bug you were hunting. Engineers call these heisenbugs.

🧊

It hangs

Output stops, CPU near 0%. That's deadlock. Look for two locks taken in different orders somewhere.

🔥

It hangs, CPU at 100%

A spin loop with no sleep in it. Somewhere a while is checking a condition as fast as the machine allows.

🎲

It works 9 times in 10

A race condition. Shared data being read or written without its lock. Run it 500 times in a loop to reproduce.

📉

One participant is silent

Starvation. Nothing is broken — one worker just never wins. Count actions per participant to confirm.

The bug that makes tests pass

This is the dangerous kind: it makes the program look healthier. Skipping the nap means forks return to the table sooner, so fewer philosophers die and the simulation survives parameters it shouldn't. A fix here may reveal starvation that was hiding behind it — that's not the fix breaking things, it's the fix telling the truth.

The edge caseOne philosopher, one fork

With n_philo == 1 there is a single fork, and eating needs two. That philosopher is doomed by the rules of the problem — but the code still has to behave correctly on the way down.

simulation.c — routine()
code 
	if (philo->data->n_philo == 1)
	{
		pthread_mutex_lock(&philo->data->forks[philo->left_fork]);
		print_status(philo, "has taken a fork");
		while (!check_stop(philo->data))
			usleep(philo->data->t_die * 1000);
		pthread_mutex_unlock(&philo->data->forks[philo->left_fork]);
		return (NULL);
	}
plain english

Special case, handled before the main loop. Only one philosopher at the table.

Take the one fork that exists and announce it — the expected output demands this line appear.

Now just wait to die. There's no second fork coming, ever. Sleep in t_die-sized chunks until the monitor declares the death and raises the stop flag.

Put the fork back and exit cleanly. Even though we're dying, the lock is released — otherwise pthread_mutex_destroy in cleanup would fail on a still-locked mutex.

🧯
Clean up on the failure path too

That unlock on the way to certain death is the mark of careful code. The most common source of resource leaks is code that tidies up correctly when things succeed and forgets entirely when they fail. Worth checking every time an AI hands you error-handling code.

🪤
A gotcha that isn't a bug

Pipe this program into head or kill it with timeout and you may see no output at all. Nothing is broken: when output goes to a pipe instead of a screen, C buffers it in blocks and an abrupt kill discards the buffer. Use the must_eat argument to make it exit on its own instead — that flushes properly.

The whole machine

Everything you've seen, assembled — plus the vocabulary that makes all of it portable to any project you touch next.

Start to finishThe complete lifecycle

1
Validate

main() checks the argument count, then ft_atoi() rejects anything that isn't a positive whole number. Nothing else runs until this passes.

2
Build the world

fill_data_struct() allocates the shared box, creates 3 global locks plus one lock per fork, and assigns each philosopher their two fork indices. Every failure path undoes the steps before it.

3
Start the clock, launch N+1 threads

Everyone's last_meal_ms is set to now, then pthread_create starts N philosophers plus the monitor.

4
The loop

Each philosopher: check neighbours → take two forks in odd/even order → record the meal → eat → release both → sleep → think → repeat.

5
The watch

Every millisecond the monitor scans for starvation and for "everyone's had enough." Either one raises the stop flag.

6
Shutdown

Philosophers see the flag, break their loops, return. pthread_join collects all N+1. Only then does destroy_data() free anything.

The three ideasWhat this project is really teaching

🔒
Shared state must be guarded — all of it, everywhere

Every field touched by more than one thread has a named lock: forks, meal records, the stop flag, the output stream. One unguarded access anywhere voids the protection everywhere.

🔄
Consistent lock ordering prevents deadlock

Odd/even fork ordering for philosophers; print-then-stop ordering for the monitor. Same principle at two scales: if everyone takes locks in the same order, a circular wait cannot form.

⚖️
Correct isn't the same as fair

should_wait() exists purely so no philosopher is left behind. A system can be free of deadlocks and races and still quietly fail one participant forever.

The last functionTaking the world apart in the right order

Every course so far has been about starting things. Here's the one that ends them — and the order of these four lines is not negotiable.

cleanup.c — destroy_data()
code 
void	destroy_data(t_data *data)
{
	if (!data)
		return ;
	destroy_forks(data);
	if (data->philos)
		free(data->philos);
	destroy_global_mutex(data);
	free(data);
}
plain english

Guard clause first. If we were handed nothing, do nothing. This one line is why main can safely call cleanup on any failure path without checking anything itself.

Destroy the fork locks, then release the memory they lived in — that happens inside destroy_forks(). Destroying a lock after freeing its memory would read memory that no longer belongs to us.

Free the philosopher records. Safe now: all their threads were joined before this function was ever called.

Destroy the three global locks — print, stop, meal. They live inside the data box, so they must go before the box does.

Free the box itself, last of all. Innermost things first, outermost things last — the exact reverse of the order they were created in.

🪆
Teardown mirrors setup, backwards

Setup went box → locks → forks → philosophers. Teardown goes philosophers → forks → locks → box. When you review cleanup code — yours or an AI's — read it bottom-up against the setup and check that it's a mirror image. Anything out of order is a crash waiting for the right moment.

VocabularyWords that work in every language

These aren't C words — they're concurrency words. They mean the same thing in Python, Go, Rust and JavaScript, and using them precisely is the fastest way to get a correct answer out of an AI assistant.

thread

An independent line of execution inside one program, sharing memory with the others.

mutex

A lock only one thread can hold at a time. Others freeze until it's released.

critical section

The lines between lock and unlock. Keep them as short as possible.

race condition

A bug whose outcome depends on which thread arrives first. Intermittent by nature.

deadlock

Two or more threads each waiting for a lock the other holds. Nothing moves, ever.

starvation

One participant never gets its turn, while everything else runs fine.

lock ordering

The rule that all threads acquire locks in one agreed sequence. The standard deadlock cure.

fine-grained locking

Many small locks over separate data, instead of one big lock over everything.

polling

Repeatedly checking on a timer rather than waiting to be notified.

watchdog

A dedicated observer that watches for failure and shuts things down. Our monitor thread.

join

Waiting for a thread to finish before continuing. Skip it and you free memory still in use.

graceful shutdown

Signalling every worker to stop, waiting for each, then releasing resources — in that order.
